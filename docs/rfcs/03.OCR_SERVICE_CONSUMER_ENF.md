# RFC 03: Serviço OCR e Consumidor da Fila

## Objetivo

Definir o comportamento do serviço responsável por consumir a fila `Documentos_para_OCR`, executar OCR em documentos PDF e PNG em português, atualizar o status do documento no banco de dados e finalizar o ciclo de vida do arquivo no filesystem.

## Contexto

O upload já é responsável por salvar o arquivo no volume Docker e enfileirar a referência do documento. O serviço de OCR deve assumir a partir daí, sem produzir nova mensagem de entrada, sem acoplar a lógica de upload ao processamento e sem depender do `main.py` da API para existir.

A proposta é ter uma instância separada do processo Python para o consumidor, com ciclo de vida próprio no Docker, escalável de forma independente e com responsabilidade exclusiva sobre a execução do OCR.

## Responsabilidades do Serviço

### Em escopo

- Consumir mensagens da fila `Documentos_para_OCR`.
- Alterar o status do documento para `processing` antes do OCR iniciar.
- Executar OCR em arquivos PDF e PNG.
- Utilizar PaddleOCR com foco em português.
- Persistir o resultado do processamento no banco.
- Alterar o status do documento para `done` ao concluir com sucesso.
- Alterar o status do documento para `error` quando houver falha no processamento.
- Remover o arquivo local do filesystem após a finalização do processamento, conforme política definida.

### Fora de escopo

- Upload do arquivo.
- Publicação da mensagem na fila.
- Reprocessamento manual na interface.
- Correção de documentos com erro pelo OCR.
- Enriquecimento com XML, caso esse fluxo esteja em outro serviço.

## Fluxo Esperado

1. O upload service salva o arquivo em disco e publica a mensagem na fila.
2. O consumidor lê a mensagem com os campos mínimos necessários, como `document_id`, `file_path` e `mime_type`.
3. O serviço atualiza o status do documento para `processing` no banco.
4. O OCR é executado sobre o arquivo.
5. O resultado é salvo no banco, incluindo texto extraído e campos que possam ser estruturados.
6. O status é atualizado para `done` em caso de sucesso.
7. O arquivo local é removido do filesystem após a conclusão.
8. Se ocorrer erro, o status deve ser marcado como `error` e o tratamento do arquivo residual deve seguir a política definida pelo time.

## Estados do Documento

O fluxo do documento deve seguir estes estados:

- `queued`: aguardando consumo da fila.
- `processing`: sob processamento pelo OCR.
- `done`: OCR concluído com sucesso.
- `error`: falha no processamento.

## Regras de Negócio

- O consumidor não deve ser o enfileirador; essa responsabilidade é exclusiva do upload service.
- O status `processing` deve ser aplicado antes de iniciar o OCR, para refletir corretamente o andamento do pipeline.
- O status final deve ser gravado sempre que o processamento terminar, com sucesso ou falha.
- O arquivo físico não deve permanecer no disco depois que o documento for concluído, salvo em caso de falha com retenção proposital para análise.
- O OCR deve ser otimizado para documentos em português.
- O consumidor deve ser executado em uma instância separada da API principal.

## Execução e Deployment

- O consumidor deve ter uma entrada própria no Docker Compose.
- O processo deve iniciar independentemente da aplicação FastAPI.
- A fila consumida deve ser a mesma utilizada pelo upload service: `Documentos_para_OCR`.
- A capacidade de escalar consumidores deve ser considerada desde o MVP.
- O consumer deve conseguir reiniciar sem perder o controle do estado do documento no banco.

## Persistência e Resultado

Além do texto OCR bruto, o serviço pode persistir metadados úteis para consulta futura, como:

- confiança média do OCR;
- idioma processado;
- tempo total de processamento;
- quantidade de páginas analisadas;
- eventuais erros de leitura por página ou bloco.

Caso o OCR produza dados estruturados, eles podem ser armazenados em JSONB, em linha com a ADR de metadados flexíveis.

## Tratamento de Erros

O RFC deve prever os seguintes cenários:

- arquivo inexistente no caminho recebido;
- documento não encontrado no banco pelo `document_id`;
- formato de arquivo não suportado;
- falha na leitura do PDF ou da imagem;
- falha na conexão com o banco;
- falha ao remover o arquivo do filesystem;
- exceção inesperada durante o OCR.

Em caso de erro, o consumer deve registrar o problema de forma rastreável e atualizar o status do documento para `error`.

## Observabilidade

Para facilitar operação e suporte, o serviço deve registrar:

- `document_id`;
- `file_path`;
- status anterior e status novo;
- início e fim do processamento;
- duração total;
- resultado da execução;
- stack trace resumido em caso de falha.

## Considerações Importantes

- O consumer precisa de uma base de status bem definida para não deixar documentos presos em `queued` ou `processing`.
- O tempo de OCR pode variar conforme o tamanho do arquivo e a quantidade de páginas.
- A remoção do arquivo local deve ocorrer somente depois que o processamento tiver um estado terminal claro.
- Se houver reprocessamento no futuro, o desenho atual deve permitir reaproveitar o documento já salvo sem novo upload.

## Status Atuais do Ambiente

```json
{
  "total": 9,
  "por_status": {
    "queued": 9,
    "processing": 0,
    "done": 0,
    "error": 0
  }
}
```

## Decisão

Adotar um serviço OCR separado da API principal, orientado a consumo de fila, com PaddleOCR em português, atualização explícita de status no banco e limpeza do arquivo local ao final do processamento.

- Criar uma tabela (document_contents) no banco para cotents relacionada aos  documents `select * from documents` que irá armazenar o conteúdo do arquivo com uma chave  estrangeira relacionando o id do documents

- Faça só o backend, não mexa em nada do frontend.
- rotas deve estar acessíveis ao swagger.
- Usar uma regex para identificar, datas, cpfs, dados e salvar no campo extracted_data 

CREATE TABLE document_contents (
    id UUID PRIMARY KEY,
    document_id UUID REFERENCES documents(id) ON DELETE CASCADE,
    raw_text TEXT,
    extracted_data JSONB, -- Aqui vão os CPFs, Datas, etc identificados
    confidence_score FLOAT,
    processing_time_seconds FLOAT,
    created_at TIMESTAMP DEFAULT NOW()
);
