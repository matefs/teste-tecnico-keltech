# RFC 01: Upload de Documentos para OCR

## Objetivo

Definir o fluxo de upload de documentos PDF e PNG para o sistema, com armazenamento local em volume Docker, persistência de metadados no banco e enfileiramento assíncrono para processamento OCR.

## Contexto

O processo atual exige que o operador envie documentos individualmente ou em lote para que eles sejam processados depois pelo OCR. Para eliminar a etapa manual, o sistema deve receber o arquivo, validá-lo no servidor, salvar o binário em um volume Docker e publicar uma mensagem na fila `Documentos_para_OCR`.

Este RFC está alinhado com as decisões arquiteturais já registradas:

- PostgreSQL como banco principal.
- Metadados e dados enriquecidos armazenados em `JSONB` quando aplicável.
- Binários salvos no File System do ambiente Docker, sem gravar o arquivo bruto no banco.

## Escopo

### Em escopo

- Upload de arquivos via `multipart/form-data`.
- Aceitação de arquivos PDF e PNG.
- Validação de conteúdo no servidor, não apenas do `Content-Type` enviado pelo cliente.
- Limite máximo de 25 MB por arquivo.
- Armazenamento do arquivo em volume Docker.
- Persistência de um registro com metadados do upload.
- Publicação de mensagem na fila `Documentos_para_OCR` após o upload bem-sucedido.
- Retorno de identificador único do documento criado.

### Fora de escopo

- Processamento OCR em si.
- Extração e enriquecimento com XML.
- Interface de consulta e relatório.
- Reprocessamento manual de documentos.

## Fluxo Proposto

1. O cliente envia o arquivo para o endpoint de upload.
2. A API valida tamanho, extensão e conteúdo real do arquivo.
3. O binário é salvo em um diretório do volume Docker.
4. O sistema cria o registro do documento no banco com o caminho do arquivo e metadados mínimos.
5. O sistema publica uma mensagem na fila `Documentos_para_OCR` com o `document_id`, `file_path` e `mime_type`.
6. A API responde com o identificador do documento e o status inicial do processamento.

## Requisitos Funcionais

### RF-01 - Upload de arquivos

O sistema deve aceitar upload de arquivos PDF e PNG via `multipart/form-data`.

### RF-02 - Validação de tipo

O sistema deve validar o tipo real do arquivo no servidor antes de salvar e enfileirar.

### RF-03 - Limite de tamanho

O sistema deve rejeitar arquivos maiores que 25 MB por arquivo.

### RF-04 - Persistência do binário

O sistema deve salvar o arquivo em um volume Docker, preservando o caminho físico para uso posterior pelo OCR.

### RF-05 - Registro do upload

O sistema deve criar um registro único para cada documento enviado.

### RF-06 - Enfileiramento assíncrono

Após um upload válido, o sistema deve publicar uma mensagem na fila `Documentos_para_OCR`.

### RF-07 - Resposta da API

A resposta do endpoint deve incluir o identificador único do documento criado e informações úteis para o operador.

## Requisitos Não Funcionais

- A operação de upload deve ser rápida e não deve aguardar o OCR terminar.
- O sistema deve retornar erros claros e códigos HTTP adequados.
- O armazenamento do arquivo deve ser previsível e compatível com execução em Docker.
- O fluxo deve ser testável de forma isolada, especialmente a publicação na fila.

## Regras de Negócio

- Apenas arquivos PDF e PNG são aceitos.
- O tamanho máximo permitido por arquivo é 25 MB.
- O arquivo original não deve ser armazenado no PostgreSQL.
- A fila `Documentos_para_OCR` deve receber a referência do arquivo salvo, não o binário.
- O consumo do OCR deve ser desacoplado do upload.

## Modelo de Dados Mínimo

O registro de documento deve guardar, no mínimo:

- `id`
- `original_filename`
- `file_path`
- `mime_type`
- `file_size`
- `created_at`
- `status`

Campos adicionais podem ser adicionados conforme o módulo evoluir.

## Contrato da Mensagem na Fila

Fila: `Documentos_para_OCR`

Exemplo de payload:

```json
{
  "document_id": "uuid-v4",
  "file_path": "uploads/2026/05/documento.pdf",
  "mime_type": "application/pdf"
}
```

### Observações sobre a fila

- A fila deve ser durável.
- A mensagem deve ser persistente.
- O consumer deve ser inicializado no `lifespan` da aplicação FastAPI.
- Se o processamento falhar, a mensagem pode ser reenfileirada.

## API Proposta

### `POST /documentos`

Recebe um arquivo em `multipart/form-data`.

#### Resposta de sucesso

```json
{
  "id": "uuid-v4",
  "status": "queued",
  "file_path": "uploads/2026/05/documento.pdf"
}
```

#### Erros esperados

- `400 Bad Request` para payload inválido ou ausência de arquivo.
- `413 Payload Too Large` para arquivo acima do limite.
- `415 Unsupported Media Type` para formato não aceito.
- `500 Internal Server Error` para falhas inesperadas no armazenamento ou no enfileiramento.

## Estratégia de Validação

- Validar a presença do arquivo na camada de entrada.
- Validar tamanho antes de gravar em disco sempre que possível.
- Validar assinatura/conteúdo do arquivo para evitar confiar apenas no MIME type.
- Bloquear extensões e formatos fora de PDF e PNG.

## Estratégia de Armazenamento

- Usar um diretório montado em volume Docker como destino dos arquivos.
- Organizar os arquivos por data ou por identificador para facilitar auditoria e manutenção.
- Persistir somente metadados e caminho físico no banco.

## Estratégia de Testes

### Testes unitários

- Validar o componente que publica a mensagem na fila.
- Validar a rejeição de formatos inválidos.
- Validar o bloqueio de arquivos acima do limite.

### Testes de integração

- Validar o endpoint de upload com multipart/form-data.
- Validar a gravação do arquivo no volume.
- Validar a criação do registro e a publicação da mensagem.

## Critérios de Aceite

- O endpoint aceita PDF e PNG via multipart/form-data.
- Endpoint disponivel no swagger do fastapi
- O sistema rejeita tipos inválidos no servidor.
- O sistema rejeita arquivos acima de 25 MB.
- O arquivo é salvo em volume Docker.
- Um registro com identificador único é criado.
- Uma mensagem é publicada na fila `Documentos_para_OCR`.
- O consumer sobe com a aplicação no `main.py`.
- Existe teste unitário cobrindo o enfileirador.

## Pendências de Implementação

- Definir o nome final do módulo de upload dentro de `src/modules`.
- Implementar o esquema Pydantic de entrada e saída.
- Implementar o repositório para persistir os metadados.
- Implementar o serviço de upload e a chamada ao publisher.
- Integrar a inicialização do consumer ao ciclo de vida da aplicação.

## Decisão

Adotar upload síncrono com persistência local do binário e enfileiramento imediato para OCR, mantendo o processamento pesado fora do ciclo da requisição HTTP.
