
# RFC 02: Frontend SPA

## Objetivo

Definir a estrutura e as regras do frontend do sistema como uma SPA em React, preparada para ser compilada antes do deploy e servida pela aplicação FastAPI.

## Contexto

O sistema precisa de uma interface simples para o operador e para o gestor acessarem os documentos, acompanharem o processamento e visualizarem dashboards. No momento, a autenticação será apenas local no frontend, usando um usuário padrão, sem integração com um backend de login.

## Escopo

### Em escopo

- Criar uma SPA em `src/frontend`.
- Usar React com Vite como base do projeto.
- Compilar a aplicação antes de iniciar o ambiente com `docker compose up`.
- Servir o `index.html` compilado pela aplicação FastAPI.
- Exibir uma tela inicial de dashboards.
- Manter sessão do usuário no navegador.
- Organizar componentes de forma modular e separada.

### Fora de escopo

- Autenticação real com backend.
- Controle de acesso por perfil no servidor.
- SSR, rotas públicas complexas ou SEO.
- Design system corporativo completo no MVP.

## Diretrizes de Arquitetura

- A aplicação deve ser uma SPA estática no lado do frontend.
- O build final deve gerar artefatos estáticos prontos para serem servidos pelo FastAPI.
- O frontend não deve depender de execução de Node em runtime.
- A experiência deve priorizar simplicidade de manutenção e baixa complexidade operacional.

## Stack Proposta

- React.
- Vite.
- Tailwind CSS ou outro framework utilitário equivalente para reduzir código repetitivo.
- Componentes pequenos e reutilizáveis.
- Persistência de sessão via `localStorage` ou mecanismo equivalente no navegador.

## Fluxo de Uso

1. O usuário acessa a aplicação e encontra a tela de login local.
2. O frontend valida credenciais padrão definidas para o MVP.
3. Após o login, a sessão é salva no navegador.
4. O usuário é direcionado para a tela principal de dashboards.
5. O navegador mantém a sessão até o logout ou expiração definida pela aplicação.

## Requisitos Funcionais

### RF-01 - Tela inicial

O frontend deve abrir na área de dashboards após a autenticação local.

### RF-02 - Login local

O sistema deve permitir login sem integração com backend de autenticação nesta fase.

### RF-03 - Persistência de sessão

A sessão do usuário deve ser preservada no navegador para evitar novo login a cada recarga.

### RF-04 - Componentização

A interface deve ser dividida em componentes pequenos e bem separados.

### RF-05 - Build para produção

O frontend deve ser compilado antes do deploy e entregue como arquivos estáticos.

### RF-06 - Servir pelo FastAPI

O FastAPI deve servir o `index.html` e os ativos compilados do frontend.

## Requisitos Não Funcionais

- A interface deve ser responsiva para desktop e funcionar de forma aceitável em telas menores.
- O código deve priorizar legibilidade e simplicidade.
- O bundle final deve ser previsível e fácil de reproduzir em ambiente Docker.
- O frontend deve evitar dependências desnecessárias.

## Regras de Negócio

- Haverá um usuário padrão para o MVP.
- A validação de login será feita apenas no frontend nesta etapa.
- A sessão deve permanecer salva no navegador enquanto não for removida pelo usuário ou pela aplicação.
- A tela principal deve focar em dashboards e visão operacional.

## Estrutura Sugerida

Pasta base: `src/frontend`

Estrutura sugerida:

- `src/frontend/src/components`
- `src/frontend/src/pages`
- `src/frontend/src/hooks`
- `src/frontend/src/services`
- `src/frontend/src/styles`
- `src/frontend/src/utils`

## Navegação da Aplicação

- Página de login local.
- Página principal com dashboards.
- Logout com limpeza da sessão local.

## Estratégia de Build e Deploy

- O build deve gerar arquivos estáticos em um diretório de saída definido.
- Esses arquivos devem ser copiados ou expostos para a camada FastAPI.
- O deploy via Docker deve assumir que o build do frontend já foi executado.

## Estratégia de Estado

- O estado de autenticação deve ser mantido no navegador.
- Informações mínimas da sessão devem ser persistidas, como usuário autenticado e flag de acesso.
- O estado visual da interface deve ser controlado localmente pela SPA.

## Estratégia de Componentes

- Componentes visuais devem ser pequenos e focados.
- Layout, cards, filtros e gráficos devem ficar separados.
- Reutilização deve ser priorizada para evitar duplicação.

## Estratégia de Estilo

- Preferir utilitários de CSS para acelerar a construção da interface.
- Evitar excesso de customização manual quando um framework resolver o problema.
- Manter consistência visual entre telas e componentes.

## Critérios de Aceite

- Existe uma SPA em `src/frontend`.
- O projeto compila antes do `docker compose up`.
- O FastAPI serve o `index.html` compilado.
- A aplicação abre em uma tela de dashboards.
- O login local funciona com usuário padrão.
- A sessão é preservada no navegador.
- Os componentes estão organizados em camadas claras.

## Pendências de Implementação

- Definir a estrutura final de rotas e páginas.
- Definir o formato exato da sessão armazenada no navegador.
- Definir a estratégia de integração entre build do frontend e FastAPI.
- Implementar o layout inicial dos dashboards.

## Decisão

Adotar uma SPA em React com Vite, build estático antecipado e entrega como arquivos servidos pelo FastAPI, com autenticação local apenas para o MVP.
